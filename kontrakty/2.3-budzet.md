## Stan i zgodność zapisów

- `Game.budget: Dictionary` — pięć poziomów 0–3, domyślnie wszystkie 1.
- `Game.budget_reservations: Dictionary` — klucz kategorii `remonty`, wartość
  `{investment: String, until_day: int, min_level: int}`. Aktywna gdy day < until_day.
- SaveGame DICTS obejmuje oba pola. Stary zapis resetuje brakujące pola do domyślnych,
  nawet po wcześniejszej rozgrywce. Normalizacja poziomów i liczb po JSON.
- `Parish.apply_effects(effects, label="", category="inne")` oraz
  `Finance.bank_entry(text, amount, category="inne")`. Historia ma category,
  stare wpisy dostają `inne`. Brak nowego formatu wersji zapisu.

## API Finance (rewizja 1)

- `default_budget() -> Dictionary`, `normalize_budget(value: Dictionary) -> Dictionary`.
- `BUDGET_CATEGORIES`: klucz → `{label, costs: Array[int], effects: Array[Dictionary], notes: Array[String]}`.
- `category_cost(id: String, level: int) -> int`;
  `weekly_expenses(plan: Dictionary = {}) -> int` (pusty = Game.budget).
- `forecast(plan: Dictionary = {}, expense: int = 0) -> Dictionary`:
  `{balance, costs, income, interest, curia_delta, days}`. Konserwatywne saldo po
  najbliższym poniedziałku: money - expense + stały yield - budget - interest.
  Taca, ofiary, losowe zdarzenia i koszty awarii nie są gwarantowane; UI mówi to wprost.
- `needs_confirmation(expense: int = 0, plan: Dictionary = {}) -> bool`:
  prognozowane saldo < 0. UI pokazuje koszt, prognozę, odsetki i kurię przed decyzją.
- `set_budget(plan: Dictionary, confirmed: bool = false) -> bool`: atomowo waliduje
  wszystkie pięć kategorii, blokadę remontów i potwierdzenie; false bez zmiany stanu.
- `reservation_text(id: String = "remonty") -> String`,
  `investment_block_reason(id: String) -> String` (pusty = dostępne).
- `can_invest(id) -> bool`; `invest(id: String, confirmed: bool = false) -> bool`.
  Nadal wymaga gotówki. false bez zmian jeśli brak potwierdzenia debetu po rachunkach.
- `natural_risk_multiplier() -> float`: remonty3 → 0; bieżące0 → 1.5; inaczej 1.
- Repairs zachowuje `can_repair`; `repair(id, confirmed=false) -> bool` z tym samym
  sprawdzeniem prognozy, kategorią remonty i bez zmian przy odmowie.

## Balans i zakres produktu

Koszty poziomów: bieżące [0,1800,2400,3000], remonty [0,800,1200,1600],
infrastruktura [0,600,900,1200], duszpasterstwo [0,600,900,1200], ludzie [0,400,600,800].
Domyślna suma 4200, maksymalna 7800; typowy tygodniowy przychód do kontroli 6000 zł
(scenariusz zwykłych mszy ma zweryfikować skalę). Każdy poziom ma opis skutku.
Bieżące: stan [-4,-2,-1,0]; remonty: stan [0,1,2,2] i poziom3 wyłącza naturalne awarie;
infrastruktura: reputacja [-1,0,1,2]; duszpasterstwo: young [-1,0,1,2];
ludzie: trad [-1,0,1,2]. Skutki sumują się podczas rozliczenia i są raportowane.
Odsetki 2% od ujemnego salda po kosztach i gwarantowanych wpływach, zaokrąglone w górę;
kuria -3 za rozliczenie z długiem. To przyjęte wartości startowe do strojenia.

Dach 8000 i nowa inwestycja `hall` (salka młodzieżowa) 7000 zajmują remonty na
14 dni od zakupu, minimum poziom1, bez dodatkowej drugiej opłaty za ten sam zakup.
Rezerwacja blokuje inne inwestycje z tej kategorii nawet przy nadmiarze gotówki,
ale nie naprawy awaryjne. Dach daje od razu young -2 (odłożona salka), salka trad -2
(odłożony dach); jawny opis przed zakupem. Salka kończy się po 4 dniach, young +10,
reputation +2; jej fizyczny slot/rozbudowa świata w 3.1, karta mówi to uczciwie.
Aktywna rezerwacja wymaga remonty >=1; zakup przy 0 zablokowany z wyjaśnieniem.
